 Investigation summary: AVX-512 JIT miscompile of the ChainedHashMap lookup                                                                                                                                                                                                                 
                                                                                                                                                                                                                                                                                            
 The original bug                                                                                                                                                                                                                                                                           
                                                                                                                                                                                                                                                                                            
 NebulaStream's merge queue failed putAndLookupKeysWithBloomFilterCompiler (rapidcheck property test, run 32721202594, seed=7646007045148759454): the compiled lookup reported a key present that was never inserted. The shrunk counterexample: 2 key fields (UINT16 nullable, INT16), 128 
 buckets, 512 entries/page, bloom filter 64 bits / 11 hashes. It failed dozens of times deterministically in-process on CI, and never on dev machines.

 Phase 2 (this session) — the actual root cause                                                                                                                                                                                                                                             
                                                                                                                                                                                                                                                                                            
 Three discoveries unblocked it:                                                                                                                                                                                                                                                            
                                                                                                                                                                                                                                                                                            
 1. The previous disassembly was of the wrong code. The dump helper skipped mappings >16 MB; the real JIT functions live in a 1 GB rwxp ORC arena — the 4 KB pages they decoded were ORC stubs. Added a jitLookupEntry() accessor (Executable::getInvocableFunctionPtr("execute")) +        
    bounds-safe window dumper → got the genuinely executed bytes.                                                                                                                                                                                                                           
 2. A host-side observer settled static-vs-dynamic. Printing the probe entry and the matched entry before/after findEntry: for every failing lookup, matched-entry: null yet the function returns true. The compare logic and chain walk are correct; the return value is corrupted.        
 3. Decoding the real machine code (skx, failing): the walk loop computes the match boolean in bl from                                                                                                                                                                                      
    ```                                                                                                                                                                                                                                                                                     
vpcmpeqw k0, xmm1, xmm0   ; operands vmovd-loaded: lanes 2..7 are zero
kshiftrb k1, k0, 1        ;   and compare EQUAL → k0 = 0xFF, not 0x03
kmovd edx, k1 ; kmovd ebx, k0
or/xor/and byte chain      ; bit 0 correct, bits 1..7 garbage
test bl, 1 ; jne <exit>    ; branch decision uses only bit 0 — correct
    ```                                                                                                                                                                                                                                                                                     
    The loop-exit phi returns the same loop-carried i1 on both edges (match edge = true; chain-end edge = known-false). On the chain-end edge the backend jumps straight to the epilogue mov eax, ebx; ret without the xorl %ebx,%ebx that every other not-found edge gets. The stale       
    garbage byte (e.g. 0x7E) is returned as the i1 → any-nonzero reads as true.                                                                                                                                                                                                             
   - Direction dependence falls out: garbage byte 0x7E vs 0xFE depending on operand order — one direction false-positive, the other happens to pass by luck of bit 0.                                                                                                                       
   - Haswell is immune because its lowering (vpmovsxwq + vmovmskpd) produces a naturally clean 2-bit mask.                                                                                                                                                                                  
   - In the original NES function the bloom filter is not semantically part of the trigger — it only perturbs register allocation enough that the unnormalized byte gets chosen for the phi (the bloom-less variant of the same walk did emit the zeroing).

 This corrects the previous session's conclusion ("not reproducible via stock llc") — that was an artifact of decoding the wrong code and testing a slightly different IR dump. It is a stock-LLVM codegen bug.                                                                             
                                                                                                                                                                                                                                                                                            
 Characterization so far:                                                                                                                                                                                                                                                                   
 - All opt levels O0–O3 (ISel-time, not an optimization pass).                                                                                                                                                                                                                              
 - LLVM 19, 20, 21, 24 (mainline) all reproduce — not a regression window, old and unfixed.                                                                                                                                                                                                 
 - Every AVX-512 target: skylake-avx512, cannonlake, icelake-client, cascadelake, cooperlake, sapphirerapids, znver4 — it's the mask-register lowering, not Intel-specific.                                                                                                                 
 - Trigger isolation: remove the loop-carried phi (return literal true/false at the two exits) → correct code; scalar icmp i16 instead of the vector icmp → correct code.                                                                                                                   
                                                                                                                                                                                                                                                                                            
 Current open question — where exactly in LLVM                                                                                                                                                                                                                                              
                                                                                                                                                                                                                                                                                            
 The i1-in-GPR contract on X86 is "0/1 in the low byte". Two candidate culprits, not yet distinguished:                                                                                                                                                                                     
                                                                                                                                                                                                                                                                                            
 1. ISel: extractelement <2 x i1> out of a mask compare emits kmovd of the full 8-bit mask and assumes "the vector has 2 elements, so bits ≥2 are irrelevant" — but they aren't irrelevant once the value is used as a scalar i1 byte. The missing and $1 should come from                  
    X86ISelLowering's EXTRACT_VECTOR_ELT lowering for vXi1 (or the X86InstrInfo.td kmov-extract patterns).                                                                                                                                                                                  
 2. Regalloc/coalescing: the i1 is created clean somewhere and the xorl-on-one-edge-only shape is a legalization/coalescing artifact (e.g. X86FixupBWInsts, which exists precisely to repair byte-width bool issues, failing to fire on this shape).                                        
                                                                                                                                                                                                                                                                                            
 Next steps to identify the LLVM code: run llc -print-after-all / -debug-only=isel on minrepro.ll for skx vs haswell to find the pass where the and $1 obligation is dropped; try variant IRs (extract lane 1 only; <8 x i16> at exact mask width; explicit zext i1 after the extract) to   
 pin the contract violation; then locate the responsible lowering in LLVM sources (the vcpkg LLVM 21 build tree is in the container) and check upstream issue trackers for the same shape.
