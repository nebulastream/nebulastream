# Reference query engine prototype

Configure with `-DNES_USE_REFERENCE_QUERY_ENGINE=ON` to use the Rust query manager in the single-node worker. The worker selects `ReferenceNodeEngine` from the separate `nes-reference-engine` module when this option is enabled. That type exposes the same methods used by the worker as the original `NodeEngine`; the compile-time branch in `SingleNodeWorker` selects the type without changing the original query engine or runtime. The `../reference-engine` checkout is required at configure and build time. Corrosion imports `rust/reference-adapter` as a static library; the reference engine itself is a path dependency and is not modified.

When building in Docker, mount `../reference-engine` at the same absolute path inside the container in addition to the usual NebulaStream mounts. The standard `nes-docker` wrapper mounts only the NebulaStream worktree. The opt-in configuration uses a separate online Cargo home because the development image's offline vendor set does not contain `crossbeam-channel`.

The adapter translates each `ExecutableQueryPlan` into a Rust `QueryPlan`, preserving source and pipeline edges. Every NebulaStream `TupleBuffer` is retained as an opaque Rust `DataBuffer`; fan-out clones the handle and the final drop releases the C++ buffer. C++ source callbacks feed the Rust source trait, and Rust pipeline execution invokes `ExecutablePipelineStage::execute` with a NebulaStream execution context. An executable plan may contain sharing IDs keyed by source origin ID and pipeline ID. The reference adapter forwards these IDs to the Rust manager; absent IDs leave the source or pipeline private to the plan.

This is an opt-in prototype with these limits:

- An initial `absorb` with empty state starts each C++ stage before the plan is submitted. Dropping the Rust pipeline stops the stage. Output from these lifecycle hooks is not routed.
- `PipelineExecutionContext::repeatTask` is unavailable. The adapter reports one worker thread and serializes calls to each C++ stage.
- A C++ source thread waits while 64 of its buffers are queued but not yet polled. This bound is fixed; the source's configured in-flight buffer limit is not applied.
- Compiled C++ stages now export one operator state tree as a `TupleBuffer` with child buffers. The Rust manager passes this opaque buffer from `emit` to `absorb`. Each stage compiles pipeline-wide `emit` and `absorb` entry points by tracing the physical operator chain. The default lowering recurses into the child; `EmitPhysicalOperator` exports its active sequence/chunk bookkeeping and debug completed-sequence set through a C++ call. Raw scans also transfer their sequence shredder state. Other stateful operators still need explicit implementations before they can be adapted safely.
- C++ stage exceptions cannot currently be propagated into the reference manager's failure event; the adapter catches them at the ABI boundary. Source errors currently end the stream.
- The adapter reports query start, running, and stop events. It does not yet reproduce the old engine's per-task or per-pipeline statistics.
- Stop is not called which is important for time based operators as they will advance the watermark

These gaps need to be resolved before this backend can replace the default engine.

## Predicate-reorder adaptation runner

Build with `-DNES_USE_REFERENCE_QUERY_ENGINE=ON`, then run `build-docker/nes-reference-engine/nes-reference-adaptation-prototype [DURATION_SECONDS]` (default: 10 seconds), or `ctest --test-dir build-docker -R '^reference-adaptation-prototype$' --output-on-failure`. The executable registers one Generator source and a Void sink, then repeatedly compiles and adapts between two SQL queries that differ only in the order of `AND` predicates. Two nested computed projections keep CSV parsing in a source input pipeline separate from the predicate pipeline. The runner shares the Generator source and transfers every pipeline, including the input formatter pipeline. Void sink uses native buffers to count received tuples. Its count is exported to a state buffer and imported into each replacement sink. The runner counts state export and import events through the statistic listener, checks that the final sink's count equals the number of tuples received across all versions, and prints interval and overall tuples-per-second throughput. A shared source owns a separate backpressure controller because the sink is replaced.

This runner fixes the catalog, SQL variants, source count, and pipeline shape. Pairing pipelines by position and sharing the source are valid for this narrow experiment; a general adaptation planner must derive semantic identities and compatible state mappings from the plans. The reported throughput includes source generation, CSV parsing, query processing, query compilation, adaptation, and sink execution, and is limited by the configured Generator rate of 100,000 tuples per second.

## Window aggregation migration runner

Run `build-docker/nes-reference-engine/nes-reference-window-adaptation-prototype OUTPUT.csv [DURATION_SECONDS]` or `ctest --test-dir build-docker -R '^reference-window-adaptation-prototype$' --output-on-failure`. The runner repeatedly replaces the same keyed, 100 ms tumbling window query while retaining the Generator source. It transfers the input formatter pipeline as well as the window and downstream pipelines. It checks every completed window against the expected `COUNT` and `SUM` for both keys, including across replacements.

Set `NES_WINDOW_ADAPTATION_DUMP_IR=1` when running the executable to write Nautilus trace and IR dumps under `/tmp/dump`. The window build pipeline's dump contains the pipeline-wide `emit` and `absorb` functions.
The prototype executable exports symbols for Nautilus's `dladdr` lookup. Nautilus demangles resolved C++ names by default. Calls to internal lambdas can still appear as addresses because `dladdr` cannot see their local symbols.

The runner supplies the optimized donor logical plan when compiling each replacement. Physical lowering pairs corresponding logical operators and checks the window type, aggregation function classes and state sizes, key types, and origin IDs before constructing the replacement window build operator. The aggregation's traced emit body walks the window store and merges each slice's worker maps using the same key comparison and aggregation `combine` functions as the probe. Its state buffer contains one contiguous sequence/watermark pair per configured origin, the next output sequence number, slice boundaries, window trigger statuses, and one combined set of entries per slice, with each entry's hash and fixed-size key/value payload. Worker map count and allocation are not part of the state. Origin IDs and origin counts come from the replacement plan and are not serialized; neither are chain pointers or aggregation kind/configuration tags. The traced absorb body uses the already validated replacement configuration, creates new slices, loads the combined entries into one map slot, and restores watermark and window bookkeeping. The probe pipeline shares the replacement handler and does not import a second copy of its state.

This first codec handles `COUNT` and `SUM` over fixed-size map entries with the same window, aggregation, and hash-map layout. The source and destination can use different worker counts because the state stores one combined entry set per slice. It rejects variable-size pages, aggregate states with child buffers, incomplete chunks, and out-of-order completed watermark sequences. `PipelineStateBufferRef` is a Nautilus cursor over a `TupleBuffer`, similar to `TupleBufferRef`. The aggregation operator lowers its loops, field reads and writes, and fixed-size payload copies directly into the pipeline-wide `emit` and `absorb` functions. Calls into C++ expose existing slice/hash-map containers, allocate destination entries, and restore handler bookkeeping. The scan operator snapshots the sequence shredder's pending entries and empty sequence ranges; retained raw buffers become child buffers of its state node. Its own serialization currently runs in a named C++ call within the compiled pipeline function. The state builder attaches child operator buffers through invoked runtime helpers. The runner also compiles and executes a small state-buffer round trip independently of adaptation. A pipeline without a donor definition compiles an `nautilus::invoke` that throws if absorb is called. The raw fixed-size key/value payload is a same-process prototype format; a portable or schema-changing migration needs typed field codecs and stronger compatibility checks. The runner pairs pipelines by position and uses an append-mode file sink to inspect results.

`AggregationSerdePropertyTest` compiles the operator's state functions through `CompiledSerdeTestHarness` and checks logical state restoration for RapidCheck-generated fixed-size key layouts, `COUNT`/`SUM` combinations, nullable sum states, multi-page slices, overlapping worker keys, and watermark positions. The harness accepts an operator-specific registration callback, so another operator can reuse the same compile, emit, and absorb steps with its own state comparison.

## Snapshot and resume runner

Run `build-docker/nes-reference-engine/nes-reference-snapshot-prototype WORK_DIRECTORY [ROWS]` or `ctest --test-dir build-docker -R '^reference-snapshot-prototype$' --output-on-failure`. The runner writes a CSV file of `ROWS` rows (default 2,000,000) and starts the keyed tumbling window query over a File source. After the first window appears, it pauses the query and checks that no output follows. It then resumes the query from the snapshot and verifies that every window appears exactly once with the values of an uninterrupted run.

`ReferenceNodeEngine::pauseQuery` adapts the query to an empty plan with one input-less snapshot pipeline. Every pipeline and the source donate state to it in one commit, so the cut is consistent. The source's state is its position: the raw bytes and the next sequence number polled before the cut. `resumeQuery` starts the recompiled plan as a detached fork. Each pipeline loads the paused pipeline's state at the same position through a replaying state source. The source restarts from the beginning, drops the consumed bytes, and renumbers the remaining buffers from the saved sequence number. The input formatter's sequence shredder therefore continues where it stopped.

The snapshot holds `TupleBuffer`s from the engine's buffer manager, so it only resumes in the same process. It is not persisted. Pausing and resuming support exactly one source and pair pipelines by position. The source replays its prefix instead of seeking, which suits any deterministic source but makes resuming a large file proportionally slower.

## Interpreted-to-compiled runner

Run `nes-reference-interpreted-to-compiled-prototype WORK_DIRECTORY [SECONDS_PER_PHASE] [SWITCHES] [file [ROWS] | generator]` (defaults: 10 seconds per phase, 4 switches, a 30,000,000-row file), or `ctest -R '^reference-interpreted-to-compiled-prototype$'`. The runner starts the window query in the Nautilus interpreter, which returns its first result without waiting for compilation. After each phase it switches the running query to the other version: interpreted to compiled, then back. Each switch is a live adaptation that transfers every pipeline's state by position, including open windows and the input formatter's partial tuples. The source is shared by all versions, so reading continues where the previous version stopped. The replacement's stages are started, which runs the JIT for the compiled version, before the commit, and the previous version keeps processing during that time.

A sampler derives the input throughput every 250 ms from the window results (each covers 50 input rows) and writes `interpreted-to-compiled-throughput.csv` to the work directory. The runner prints each phase's median, which ignores the catch-up on queued input right after a switch to the faster version. Finally it verifies that the output is the exact prefix of an uninterrupted run. Plot the timeline with `plot_interpreted_compiled_throughput.py THROUGHPUT.csv OUTPUT.png`, which requires matplotlib.

The default `file` source is long enough for the default schedule in a Debug build. The `generator` source is unbounded, but in a Debug build it produces only about 26,000 rows/s, so it caps the compiled measurement.

`PrototypeQuery.hpp` holds the catalog, query, input, and output-checking code shared with the snapshot runner.
